# Дорожная карта frontend MVP

Этот документ задаёт порядок крупных этапов. Он не показывает текущий статус
задач и не заменяет SourceCraft: исполнители, зависимости между конкретными
задачами и результаты проверки живут в трекере.

Архитектурные границы frontend описаны в
[`frontend.md`](../02-architecture/frontend.md), REST-схема — в
[`rest-api.md`](../03-contracts/rest-api.md), правила оформления — в
[`frontend-styles.md`](../02-architecture/frontend-styles.md).

## Граница frontend MVP

MVP v1 — живая карта на реальных данных REST API. Пользователь должен увидеть
активные H3-ячейки в текущем viewport, выбрать ячейку и перейти к изменявшимся
статьям.

В первую поставку не входят:

- исторический dashboard — он начинается после отдельного контракта и источника
  данных;
- отдельная адаптивная полировка — сначала завершается рабочий desktop MVP;

## Порядок работ над frontend

Этапы идут последовательно по зависимостям, но не обязаны соответствовать одной
ветке или одному PR. Детальное разбиение выполняется в трекере.

### 1. Подготовить интеграционную границу

Перед подключением страницы к сети нужно:

- считать репозиторный REST-контракт единственным источником формата запроса и
  ответа;
- согласовать с backend найденные расхождения, не выбирая новое значение на
  стороне frontend молча;
- закрыть расхождение в типе и допустимом диапазоне `zoom`, обновив контракт и
  реализацию одним согласованным изменением;
- определить явное преобразование transport DTO в модель, которую получают
  карта и sidebar;
- договориться, какие события Яндекс.Карт дают актуальные `bbox` и `zoom`.

Результат этапа: UI не придумывает отсутствующие поля, а форма данных между API
и визуальными компонентами понятна до начала live-интеграции.

### 2. Подключить вертикальный срез живой карты

Нужно провести один реальный ответ через весь frontend:

1. Получить `bbox` и `zoom` из viewport карты.
2. Передать параметры в существующий API-адаптер.
3. Преобразовать ответ в согласованную visual/domain model.
4. Отобразить H3-полигоны.
5. Показать события выбранной ячейки и рабочие ссылки на статьи.
6. Удалить старые fixtures и модель `Hotspot`, когда у них не останется
   потребителей.

Результат этапа: изменение viewport создаёт корректный запрос, а ответ backend
виден на карте и в sidebar. Пустой список считается нормальным результатом.

### 3. Сделать live-обновление устойчивым

После первого рабочего запроса добавляются:

- debounce частых событий viewport;
- polling с интервалом из REST-контракта;
- запрет наложения одинаковых запросов;
- отмена запроса при смене viewport или unmount;
- защита от ответа для устаревшего viewport;
- сохранение последних успешно загруженных данных при ошибке фонового refresh.

Результат этапа: более старый ответ не может заменить новые данные, polling не
создаёт гонки, а cleanup корректно работает в React `StrictMode`.

### 4. Закрыть состояния и взаимодействие карты

Экран должен явно обрабатывать:

| Состояние | Что видит пользователь |
|---|---|
| загрузка API карты | стабильный shell и индикатор загрузки |
| первичная загрузка данных | loading без скачка layout |
| данные получены | полигоны и события выбранной ячейки |
| результат пуст | понятное empty-состояние |
| фоновое обновление | прежние данные и ненавязчивый refresh |
| ошибка без данных | сообщение об ошибке и Retry |
| ошибка после успеха | прежние данные и предупреждение |
| выбранная ячейка исчезла | выбор сброшен или явно помечен устаревшим |

Список ячеек и статьи должны оставаться доступными через семантические
`button` и `a`; polling не должен самопроизвольно уводить клавиатурный focus.
Правила визуальных состояний не повторяются здесь и берутся из style guide.

Результат этапа: пользователь понимает состояние системы и может восстановиться
после ошибки без перезагрузки страницы.

### 5. Завершить desktop MVP

На этом этапе доводится согласованный desktop viewport:

- shell, Header, карта и sidebar не конфликтуют по layout;
- `/map`, `/dashboard` и Not Found остаются самостоятельными маршрутами;
- dashboard честно сообщает, что аналитика ещё недоступна;
- основные действия работают мышью и клавиатурой;
- новые SCSS Modules соответствуют frontend style guide.

Полноценная адаптивность не расширяет этот этап. Исправляются только поломки,
которые мешают использовать согласованный desktop MVP.

Результат этапа: основной сценарий карты можно последовательно показать на
демо без моковых production-данных.

### 6. Проверить качество и интеграцию

Перед завершением MVP нужно:

- выполнить актуальные `build` и `lint` из `frontend/package.json`;
- подтвердить, что backend endpoint читает live-источник, а не возвращает
  захардкоженный contract mock; без этого продуктовый MVP и финальное демо не
  считаются готовыми;
- проверить browser → frontend `/api` → backend на реальном ответе;
- проверить первоначальную загрузку, empty, error, Retry и обновление viewport;
- проверить прямое открытие и reload frontend-маршрутов на выбранном hosting;
- добавить минимальные автоматические проверки для сериализации query,
  преобразования DTO и защиты от устаревшего ответа, предварительно настроив
  test runner отдельным небольшим изменением;
- обновить README и
  [`demo-scenario.md`](../06-demo/demo-scenario.md) по реально
  воспроизводимому запуску.

Результат этапа: сценарий воспроизводится из чистого clone, а выполненные и
невыполненные проверки названы явно.

## После MVP v1

### Адаптивность

Responsive polish начинается отдельным этапом после рабочего desktop MVP.
Приоритеты и критерии этого этапа уже описаны в
[`frontend-styles.md`](../02-architecture/frontend-styles.md).

### Dashboard

Работа начинается только после согласования B и F1 исторического REST-контракта
и подтверждения источника данных. Затем отдельным вертикальным срезом
реализуются period selection, summary, список статей и состояния
loading/error/empty.

Frontend не вычисляет отсутствующую историческую аналитику из окна живой карты
и не показывает fixtures как production-результат.

## Критические зависимости и риски

| Зависимость или риск | Что с ним делать |
|---|---|
| REST-документ и backend расходятся | согласовать B и F1 до реализации спорного поведения |
| REST DTO отличается от текущей модели карты | использовать явное преобразование, не смешивать поля |
| backend ещё не отдаёт реальные live-данные | проверять UI на согласованном ответе, не маскировать блокер fallback-данными и не объявлять продуктовый MVP готовым |
| production hosting не настроил SPA fallback | проверить прямое открытие маршрутов до демо |
| Яндекс.Карты не загрузились или нет API key | показать контролируемую ошибку вместо сломанного экрана |

## Как отслеживать выполнение

Для каждого этапа создаются проверяемые задачи по форме из
[`process/taskflow.md`](../../process/taskflow.md). В этом документе не ставятся
галочки и не записываются SHA: актуальный статус виден в трекере и Git.

Общий критерий готовности задачи находится в
[`process/workflow.md`](../../process/workflow.md). Команды frontend перечислены
в [`frontend/README.md`](../../frontend/README.md).
