# Frontend: правила работы с кодом

## Область действия

Правила действуют для всех файлов внутри `frontend/`.

## Что прочитать перед изменениями

1. [frontend.md](frontend.md) — архитектура frontend.
2. [../03-contracts/rest-api.md](../03-contracts/rest-api.md) — контракт
   бэкенда и фронтенда.
3. [frontend-styles.md](frontend-styles.md) — правила написания стилей.
4. [frontend-implementation-notes.md](frontend-implementation-notes.md) —
   почему код написан именно так.

Не копируй сюда схемы контракта, правила процесса или гайд по стилям.

## Граница REST-контракта

- Источник истины по REST внутри репозитория —
  [../03-contracts/rest-api.md](../03-contracts/rest-api.md).
- Изменение REST меняет контракт в той же задаче и согласуется с бэкендом
  до реализации.
- Если контракт, бэкенд, frontend-адаптер или внешняя схема расходятся,
  зафиксируй расхождение. Не выбирай новый контракт молча и не маскируй
  расхождение в UI.
- Не добавляй в UI поля ответа, которых нет в согласованном контракте.
- Не выдавай моковые данные за резервный источник live-данных.
- Разделяй транспортный DTO и визуальную/доменную модель, если у них разные
  формы или ответственность.

## Границы кода

- `src/app/` отвечает за запуск приложения, роуты и общий каркас.
- `src/pages/` собирает страницу и владеет локальным состоянием маршрута.
- `src/components/` получает данные и callbacks через props. Обычные
  UI-компоненты не выполняют HTTP-запросов.
- `src/api/` отвечает за транспортные DTO, сериализацию query-параметров и
  поведение HTTP-клиента.
- Добавляй feature-слой, когда реальному сценарию нужна оркестрация: polling,
  отмена запросов или общее асинхронное состояние. Не разворачивай полную FSD
  заранее.

## React и жизненный цикл карты

- Render должен оставаться чистым. Создавай карты, таймеры, запросы и подписки
  только в эффектах или специализированных hooks.
- Каждый внешний ресурс должен иметь cleanup, корректный в React `StrictMode`.
- Храни экземпляры Yandex Map и её features в refs внутри адаптера карты.
- Передавай данные карты, выбранный объект и callbacks через props.
- Вычисляй производные значения из props/state во время render, не дублируй их
  в state.
- Не позволяй устаревшему ответу для старого viewport заменить новые данные.
  При ошибке фонового обновления сохраняй последние успешно загруженные данные.

## Зависимости

Не добавляй глобальный store, query-библиотеку, библиотеку графиков, Storybook
или общий UI-пакет без подтверждённого сценария и согласованной причины. Для
одного приложения отдельная библиотека компонентов не создаётся.

## Стили и доступность

Следуй [frontend-styles.md](frontend-styles.md). Не повторяй здесь правила
BEM, токенов и интерактивных состояний.

Предпочитай нативные семантические элементы. Не убирай клавиатурный focus без
равноценного видимого состояния `:focus-visible`.

## Проверка и документация

- Используй только scripts, которые действительно объявлены в `package.json`.
  Не придумывай и не заявляй несуществующую команду тестов.
- Запускай проверки, относящиеся к изменённым файлам, и точно сообщай, что было
  и не было запущено.
- Не заявляй production SPA fallback или поведение в браузере без проверки в
  соответствующем окружении.
- Архитектурные документы содержат стабильные решения и причины, а не имена
  веток, хеши коммитов, датированные таблицы статуса или бэклог реализации.
- При изменении архитектурного решения в той же задаче обновляй документацию.

## Комментарии

- Комментариев в коде нет. Причины решений — выбор константы, обход подвоха,
  граница применимости, осознанное упрощение — живут в
  [frontend-implementation-notes.md](frontend-implementation-notes.md) и
  привязаны там к файлу и символу.
- Добавляешь неочевидное решение — добавь пункт в этот документ, а не
  комментарий в файл. Потребность написать комментарий означает, что в
  документе не хватает пункта.
