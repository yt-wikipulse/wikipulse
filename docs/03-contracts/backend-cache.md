# Контракт: RecentEventsCache

Стык внутри бэкенда. Одна половина трека наполняет кэш из очереди, вторая
читает его и отдаёт наружу. Меняется с согласия обеих сторон.

## Интерфейс

```java
public interface RecentEventsCache {
    /** Кладёт событие. Вызывает только поллер. */
    void put(EnrichedEvent event);

    /** Снимок на момент вызова: ключ — h3_r9, значение — события ячейки. */
    Map<String, List<EnrichedEvent>> snapshot();
}
```

Чтение — снимком, а не по ключам: карта сворачивает ключи кэша вверх до нужной
резолюции, поэтому нужен обход всех ячеек. Разворот запроса вниз до r9
неприменим — от r3 до r9 получается около 117 тысяч дочерних ячеек на одну.

## Кто за что отвечает

| Гарантирует запись | Может рассчитывать чтение |
|---|---|
| ключ — H3-индекс уровня 9, как пришёл из очереди | не проверяет формат ключа |
| в кэше нет правок старше 30 минут по `event_ts` | не фильтрует по времени |
| нет дублей по `event_id` | не дедуплицирует |
| коллекции иммутабельны, обход безопасен | не копирует защитно |
| ячейка без событий исчезает из снимка | не проверяет пустые списки |
| пустой кэш — пустая мапа | не проверяет на `null` |
| события отсортированы по `event_ts`, новые первыми | может обрезать длинные списки |
| событий без `event_ts` и «из будущего» нет | не проверяет время на осмысленность |

География, bbox и резолюции — не зона записи. Структура хранения, вытеснение
и выбор библиотеки — не зона чтения.

## Размер

Потолка нет: размер ограничивает само окно в 30 минут. Сколько это ячеек
на четырёх вики — станет видно на первом живом запуске; до тех пор лимит
задавать не нужно, это была бы настройка под неизмеренную нагрузку.

## Время

Окно считается по `event_ts` — времени самой правки, а не времени, когда её
прочитал поллер. Отставание пайплайна из-за этого видно честно: если джоба
обогащения встала, карта пустеет, а не показывает старое как свежее.

`event_ts` приходит в **unix-секундах**. Часы бэкенда — в миллисекундах,
поэтому сравнение идёт в секундах через `getEpochSecond()`.

Порядок в деке — порядок прихода, по времени правки он не отсортирован:
поллер читает пачками, и событие может прийти позже более свежего. Поэтому
и фильтрация, и вытеснение проходят по всей ячейке, а сортировка делается
при сборке снимка.

Два случая отбрасываются при записи, с записью в лог:

- `event_ts <= 0` — поле не пришло; по нему нельзя посчитать окно, и событие
  никогда бы не появилось на карте;
- `event_ts` больше текущего времени более чем на минуту — часы источника
  убежали; такое событие не протухло бы никогда и осталось бы в кэше навсегда.

Минута допуска нужна, чтобы обычное расхождение часов не отбрасывало живые
правки.
