# Контракт: REST API

Граница между бэкендом и фронтендом. Два экрана: живая карта и дашборд.

## Общие правила

- Базовый путь: `/api/v1`.
- Формат: JSON, имена полей — `snake_case`.
- Карта обновляется поллингом раз в 2,5 секунды, дашборд — по запросу.
- Все эндпоинты — `GET`, тела запроса нет ни у одного.

Записи ответов объявлены в коде в camelCase, а в `snake_case` их переводит
единственный ключ конфигурации `spring.jackson.property-naming-strategy:
SNAKE_CASE`. Тронуть его — молча сломать фронтенд.

## Ошибки

Формат — Problem Details (RFC 9457), `Content-Type: application/problem+json`:

```json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "zoom must be between 0 and 30"
}
```

| Код | Когда | `detail` |
|---|---|---|
| `400` | не прошла проверка параметров эндпоинта | человекочитаемая причина |
| `400` | нет обязательного параметра или он не парсится | текст Spring про параметр |
| `404` | неизвестный путь | текст Spring |
| `405` | метод не поддерживается | текст Spring |
| `503` | не прочитались таблицы YT | `storage is temporarily unavailable` |
| `500` | всё остальное неожиданное | `internal error` |

Наружу из `5xx` уходит статичный текст без подробностей: пути таблиц, имя
кластера и сообщение YT остаются в логе. Ошибки маршрутизации и биндинга
отдаются честными `4xx`, а не `500`, — почему это потребовало отдельного
решения, написано в
[backend-implementation-notes.md](../02-architecture/backend-implementation-notes.md),
раздел `error/GlobalExceptionHandler.java`.

## `GET /api/v1/hexagons/active`

Активность в видимой части карты. Фронт присылает прямоугольник экрана
и текущий зум, бэкенд сам выбирает резолюцию H3.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `min_lng` | number | да | западная граница экрана |
| `min_lat` | number | да | южная граница |
| `max_lng` | number | да | восточная граница |
| `max_lat` | number | да | северная граница |
| `zoom` | integer | да | зум карты, бэкенд переводит его в резолюцию H3 |

Значений по умолчанию нет ни у одного параметра: отсутствие любого — `400`.

Пример:

```
GET /api/v1/hexagons/active?min_lng=37.31&min_lat=55.57&max_lng=37.85&max_lat=55.91&zoom=10
```

Ответ:

```json
{
  "hexagons": [
    {
      "h3_index": "8611aa7afffffff",
      "events_count": 1,
      "events": [
        {
          "id": "ruwiki|142857001",
          "title": "Москва",
          "url": "https://ru.wikipedia.org/wiki/Москва",
          "length_update": 234,
          "diff_url": "https://ru.wikipedia.org/w/index.php?diff=142857001&oldid=142856900",
          "event_ts": 1788080804
        }
      ]
    }
  ]
}
```

Query-параметры в ответе не дублируются: резолюцию фронт знает по своему зуму.

### Поля события

| Поле | Что означает |
|---|---|
| `id` | `event_id` из очереди: вики и номер ревизии |
| `title` | заголовок статьи |
| `url` | ссылка на статью |
| `length_update` | прирост длины статьи в байтах, бывает отрицательным |
| `diff_url` | ссылка на диф правки; фронт достаёт из неё номера ревизий |
| `event_ts` | время правки, unix-секунды |

`events_count` — **полное** число событий ячейки за окно, а массив `events`
обрезан до 50 самых свежих (`app.live.hexagon-events-cap`). Счётчик и длина
массива расходятся штатно, это не рассинхрон.

### Проверка параметров

| Условие | Ответ |
|---|---|
| `min_lng >= max_lng` или `min_lat >= max_lat` | `400`, `min_lng/min_lat must be less than max_lng/max_lat` |
| `zoom` вне `0…30` | `400`, `zoom must be between 0 and 30` |

Границы зума берутся из `app.live.zoom-min` и `app.live.zoom-max`.
Прямоугольник, пересекающий 180-й меридиан, не поддерживается: у него
`min_lng > max_lng`, и запрос отбивается как невалидный.

### Что делает бэкенд

1. Переводит `zoom` в целевую резолюцию H3 (`H3GeoService.resolutionZoom`).
2. Берёт снимок кэша целиком: ключ — `h3_r9`, значение — события ячейки.
3. Сворачивает каждый ключ вверх до целевой резолюции (`cellToParent`)
   и складывает события в бакеты по родительской ячейке.
4. Оставляет только бакеты, чья ячейка пересекает прямоугольник экрана.
5. Сортирует события каждой ячейки по `event_ts` (новые первыми) и обрезает
   список до потолка.

Разворот запроса вниз, до всех дочерних ячеек уровня 9, не используется: от
резолюции 3 до 9 получается около 117 тысяч потомков на одну ячейку. Проще
обойти весь кэш — его размер ограничен окном в 30 минут.

Пересечение с экраном считается с двух сторон: ячейка попала в экран, если
внутри прямоугольника лежит её центр или любая из шести вершин; экран попал
в ячейку, если хотя бы один из четырёх его углов лежит внутри неё. Вторая
половина нужна для сильно отдалённой карты, когда экран целиком помещается
в одну ячейку.

Вся арифметика H3 живёт в одном классе `H3GeoService`.

### Лестница зума

| `zoom` | Резолюция H3 |
|---|---|
| `0…6` | 3 |
| `7` | 4 |
| `8…9` | 5 |
| `10…11` | 6 |
| `12…13` | 8 |
| `14…30` | 9 |

Ступени задаются ключами `app.live.zoom-r3-max`, `zoom-r4-max`, `zoom-r5-max`,
`zoom-r6-max`, `zoom-r8-max`; резолюция 7 в лестнице пропущена. Подробности —
в [backend-implementation-notes.md](../02-architecture/backend-implementation-notes.md).

### Окно

События хранятся в кэше **30 минут**. Ячейки без событий за это окно
в ответ не попадают: пустой список `hexagons` — нормальный ответ, а не ошибка.
Гарантии кэша — в [backend-cache.md](backend-cache.md).

## `GET /api/v1/dashboard`

Историческая аналитика поверх витрин. Витрины пересчитываются по расписанию,
поэтому поллинг не нужен — запрос делается при открытии экрана и при смене
периода.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `period` | `24h` \| `7d` \| `30d` | да | окно агрегации |
| `limit` | integer, 1–100 | нет | длина топов, по умолчанию 10 |

Оба значения проверяет контроллер, до похода в сервис и кэш: это граница
доверия, и дублировать проверку в реализациях сервиса незачем.

Пример:

```
GET /api/v1/dashboard?period=24h
```

Ответ:

```json
{
  "period": "24h",
  "generated_at": 1788080783,
  "bucket_seconds": 3600,
  "total_edits": 25728,
  "trends": [
    { "bucket_ts": 1787994000, "edits_count": 1071 }
  ],
  "top_articles": [
    {
      "title": "Federal Reserve",
      "url": "https://en.wikipedia.org/wiki/Federal_Reserve",
      "edits_count": 18420
    }
  ],
  "top_geo": [
    {
      "h3_parent": "862664c1fffffff",
      "top_title": "Teotihuacán",
      "top_url": "https://en.wikipedia.org/wiki/Teotihuacan",
      "edits_count": 9840,
      "articles_count": 312
    }
  ]
}
```

### Поля

| Поле | Что означает |
|---|---|
| `period` | эхо запроса, чтобы клиент не сверялся со своим состоянием |
| `generated_at` | когда бэкенд собрал этот ответ, unix-секунды |
| `bucket_seconds` | шаг между точками `trends`, зависит от периода |
| `total_edits` | сумма `edits_count` по всем точкам `trends` |
| `trends[].bucket_ts` | начало интервала, unix-секунды |
| `top_articles[]` | самые правимые статьи периода |
| `top_geo[].h3_parent` | H3-ячейка резолюции 6 |
| `top_geo[].top_title` | самая правимая статья внутри ячейки |
| `top_geo[].articles_count` | сколько разных статей затронуто в ячейке |

`generated_at` — это **время сборки ответа**, а не время пересчёта витрин.
Реальную свежесть данных знает только пайплайн, и наружу она пока не
отдаётся: у витрин есть атрибут `@computed_at`, но бэкенд его не читает.
С учётом минутного кэша ответа значение отстаёт от текущего времени не
больше чем на минуту.

Время везде в unix-секундах — как `event_ts` в очереди. ISO-строк в дашборде
нет намеренно: точки графика удобнее считать числами.

### Периоды и витрины

Наружу отдаются читаемые `24h`, `7d`, `30d`. Топы хранят период строкой
в часах, поэтому бэкенд переводит значение перед запросом:

| Запрос | В витрине |
|---|---|
| `24h` | `24h` |
| `7d` | `168h` |
| `30d` | `720h` |

Перевод касается только `top_articles` и `top_geo`. У `marts/trends` колонки
периода нет вовсе: точки выбираются условием
`bucket_ts >= now - длительность периода`. Схемы — в
[yt-schemas.md](yt-schemas.md).

Если строк за нужный период в витрине нет, ответ придёт пустым — см. ниже.

### Шаг графика

`bucket_seconds` не выдумывается клиентом, его задаёт бэкенд:

| `period` | `bucket_seconds` | Точек в графике |
|---|---|---|
| `24h` | 3600 (час) | до 24 |
| `7d` | 3600 (час) | до 168 |
| `30d` | 86400 (сутки) | до 30 |

Причина в читаемости: месяц почасовыми точками — это 720 значений, график
превращается в шум. Витрина хранит только часовые строки, поэтому суточные
точки для `30d` бэкенд складывает сам, уже после чтения.

Часового окна нет намеренно: за час получилась бы одна точка. Более мелкий
шаг потребовал бы отдельного пересчёта в пайплайне, а для MVP это
не окупается.

### Пустые данные

Витрина может быть ещё не посчитана — тогда `trends`, `top_articles`
и `top_geo` приходят пустыми массивами, а `total_edits` равен нулю.
Это нормальный ответ, не ошибка. Пустой экран дашборда объясняет пользователю,
что данных пока нет.

### Ошибки

| Условие | Ответ |
|---|---|
| `period` вне `24h`, `7d`, `30d` | `400`, `period must be one of 24h, 7d, 30d` |
| `limit` вне `1…100` | `400`, `limit must be between 1 and 100` |
| нет `period` или `limit` не число | `400` от Spring |
| витрины недоступны | `503` |

Устаревшие данные вместо ошибки не отдаются: показывать вчерашние цифры
без пометки значит врать. Что кэшируется и на сколько — в
[dashboard-cache.md](dashboard-cache.md).

### Согласованность

Три блока читаются из трёх разных витрин отдельными запросами. Между ними
батч-джоба может пересчитать часть таблиц, поэтому блоки способны относиться
к соседним пересчётам. Для почасовых агрегатов это незаметно, но `total_edits`
считается **из тех же точек `trends`**, что уехали в ответ, — чтобы сумма
на экране всегда сходилась с графиком.

### Профиль mock

Эндпоинт отвечает и без кластера: на профиле `mock` его обслуживает
`MockDashboardService`, который отдаёт снятые с боевого стенда фикстуры
из `backend/src/main/resources/fixtures/`. Форма ответа та же, `limit`
режет топы так же; `503` на этом профиле не бывает.

## `GET /api/v1/config`

Настройки, которые фронтенд получает в рантайме: ключ JavaScript API
Яндекс Карт.

Параметров нет.

Ответ:

```json
{
  "ymaps_api_key": "<ключ из Кабинета разработчика>"
}
```

Ключ приходит из окружения бэкенда (`app.ymaps.api-key`, переменная
`YMAPS_API_KEY`), а не из сборки фронтенда. Смена ключа поэтому не требует
пересборки образа `web` — достаточно поменять значение в окружении и поднять
контейнеры заново. Это же делает проект пригодным для форка: тот, кто
клонирует репозиторий, подставляет свой ключ, не трогая код.

Ключ публичный — он уходит в браузер и виден в отладчике. От чужого
использования его защищает ограничение по HTTP Referer в кабинете Яндекса,
где для ключа прописан домен сайта. Условия использования JS API — в
[data-sources.md](data-sources.md).

### Ключ не задан

Отдаётся `200` с пустой строкой:

```json
{
  "ymaps_api_key": ""
}
```

Отсутствие ключа не ошибка запроса, поэтому не `5xx`. Карта в этом случае
не инициализируется и показывает ошибку загрузки, остальная страница работает.

## Чего в API нет

**Дифа правки.** Текст изменений фронт берёт напрямую из MediaWiki Action API
браузером, минуя бэкенд, — см. [data-sources.md](data-sources.md).

**Разрезов по языку, боту, стране и типу места.** Событие отдаётся полями
`id`, `title`, `url`, `length_update`, `diff_url`, `event_ts` — ровно тем, что
лежит в очереди. Всё остальное сначала появляется в
[yt-schemas.md](yt-schemas.md), потом здесь.
