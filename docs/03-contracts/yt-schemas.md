# Контракт: схемы таблиц и очередей YT

Граница между пайплайном и бэкендом. Меняется с аппрувом обеих сторон:
P2 пишет данные, B их читает.

Имена полей в YT — `snake_case`. В Java они отображаются в `EnrichedEdit`
и `AggregateRow`, camelCase появляется только там.

## Объекты

| Путь | Тип | Пишет | Читает |
|---|---|---|---|
| `Q_ENRICHED` | queue | SPYT-джоба обогащения | бэкенд, батч-джоба |
| `aggregates` | static | батч-джоба | бэкенд |

Полные пути на кластере фиксируются в `local-setup.md` и задаются конфигом,
в коде не хардкодятся.

## Q_ENRICHED

Главный объект контракта: из него бэкенд строит карту.

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `event_id` | string | да | `{wiki}\|{revision_new}`, ключ дедупликации |
| `event_ts` | int64 | да | время правки, unix-секунды UTC |
| `wiki` | string | да | `enwiki`, `ruwiki` |
| `lang` | string | да | `en`, `ru` |
| `title` | string | да | заголовок с пробелами, не подчёркиваниями |
| `type` | string | да | `edit` или `new` |
| `user` | string | нет | логин редактора, `null` у анонимов |
| `bot` | boolean | да | правка от бота |
| `delta_len` | int64 | да | `length_new − length_old`, байт |
| `lat` | double | да | координата места |
| `lon` | double | да | координата места |
| `country_qid` | string | нет | QID страны из Wikidata `P17` |
| `place_type_qid` | string | нет | QID типа места из Wikidata `P31` |
| `h3_r3` | string | да | ячейка уровня региона |
| `h3_r6` | string | да | ячейка уровня города |
| `h3_r9` | string | да | ячейка уровня квартала |

**Правки без координат в очередь не попадают.** Джойн со справочником —
inner: статья без геометки отбрасывается на стороне пайплайна, бэкенд
фильтрацией не занимается.

Следствие для дашборда: все счётчики считают правки **о местах**, а не весь
поток Википедии. `total_edits` будет заметно меньше реального объёма правок —
это ожидаемо, а не потеря данных.

Из-за этого в `EnrichedEdit` становятся лишними поле `hasGeo` и nullable-типы
у `lat` и `lon` — их можно убрать при наполнении `YtQueuePoller`.

**`url` в очереди нет.** Бэкенд собирает его сам: `wiki` → домен
(`enwiki` → `en.wikipedia.org`), `title` → путь с заменой пробелов на `_`.
Это ответственность `Urls`.

**QID не резолвятся в пайплайне.** В очереди лежит стабильный ключ Wikidata,
в ISO-код его переводит бэкенд по справочнику-ресурсу (около двухсот строк,
генерируется один раз). Так пайплайн не тянет второй справочник из дампа,
а маппинг правится выкаткой бэкенда, без пересчёта очереди.

### Чтение очереди

Бэкенд читает `Q_ENRICHED` консьюмером `c_rt`. Фоновый поллер раз в секунду
забирает новые строки, кладёт их в `RecentEditsStore` и продвигает оффсет
консьюмера. Оффсет двигается **после** успешной укладки в кэш, иначе при
рестарте потеряется окно.

Гарантия — at-least-once: при падении между укладкой и продвижением оффсета
строка придёт повторно. Дедупликация по `event_id` на стороне бэкенда.

## aggregates

Единая витрина дашборда, батч-джоба пересчитывает её раз в час.

**Хранятся только часовые строки.** Дневных строк нет: значения за сутки
и за неделю бэкенд складывает из 24 и 168 часовых. Так витрина не дублирует
одни и те же данные в двух гранулярностях и не расходится сама с собой.

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `bucket_start` | int64 | да | начало часа, unix-секунды UTC |
| `lang` | string | нет | `null` — строка по всем языкам |
| `country_qid` | string | нет | `null` — строка по всем странам |
| `edits_count` | int64 | да | число правок |
| `users_count` | int64 | да | уникальных редакторов за час |
| `pages_count` | int64 | да | уникальных статей за час |
| `new_articles` | int64 | да | правок с `type = new` |

Ключ строки — `bucket_start` и разрезы `lang` и `country_qid`. Разрез,
по которому агрегат не считается, помечается `null`.

Обновляется раз в час. Бэкенд кэширует результат на 60 секунд.

### Складывание за окно

`edits_count` и `new_articles` аддитивны — суммируются по часам без потерь.

`users_count` и `pages_count` не аддитивны: один редактор, правивший в трёх
разных часах, даст три в сумме вместо одного. За окно больше часа это
**верхняя оценка**, а не точное число. Для MVP приемлемо, но на дашборде
подписывать как «правок от редакторов» и «статей затронуто», а не
«уникальных».

### Как эндпоинты ложатся на витрину

| Эндпоинт | Фильтр |
|---|---|
| `/api/dashboard/summary` | `lang = null`, `country_qid = null` |
| `/api/dashboard/top-places` | `country_qid != null`, сумма по окну, топ по правкам |
| `/api/dashboard/trends` | глобальная строка, по одной точке на час |

`window` выбирает диапазон часовых строк: `1h` — одна, `24h` — 24, `7d` — 168.

## Соглашения

- Время в YT — `int64`, unix-секунды UTC. В ISO 8601 конвертирует бэкенд.
- Координаты — `lat` и `lon`, `double`, WGS84.
- `null` означает «разрез не применён», а не «данных нет».

## Расхождения с rest-api.md

Требуют правки контракта REST отдельным PR:

1. **`country_qid`** — в REST отдаётся наружу как есть, с пометкой «без
   резолва». Резолв делает бэкенд, наружу должен идти `country` с ISO-кодом.
2. **`place_type_qid`** — наружу не отдаётся вовсе, из модели `Edit` убирается.
3. **`top_wiki` в `summary`** — витрина разрезана по `lang`, не по `wiki`.
   Либо переименовать в REST, либо добавить разрез.
4. **`T_MART_top_country`, `T_MART_top_wiki`, `T_MART_edits_per_hour`** — этих
   таблиц нет, витрина одна и называется `aggregates`.
