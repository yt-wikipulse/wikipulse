# WikiPulse: Отчёт о реализации backend-части

## Что хотел заказчик

**Продуктовая цель:** живая карта мира, где в реальном времени загораются места, чьи статьи в Википедии правят прямо сейчас. Плюс дашборд с исторической аналитикой. Open-source, forkable проект — точка входа в YTsaurus для студентов и разработчиков.

**Технические требования:**

- **YTsaurus как единая платформа** — без зоопарка из Kafka \+ Postgres \+ Spark \+ warehouse
- **REST API** (поллинг каждые 2–3 секунды для карты, по запросу для дашборда)
- **Два экрана:** живая карта \+ дашборд (тренды, топ-статьи, топ-гео)
- **Потоковая обработка:** Wikipedia SSE → SPYT stream JOIN → SPYT stream windowing → REST API
- **Батчевая обработка:** архивация истории → SPYT batch aggregations → витрины дашборда

## Что реализовали

### 1\. Живая карта (`/api/v1/hexagons/active`)

- `LiveMapService` — фолдинг событий из кэша в гексагоны нужной резолюции (r3/r6/r9) в зависимости от зума
- `RecentEventsCache` — окно 30 минут, дедуп по `event_id`, иммутабельные снапшоты
- `H3GeoService` — перевод зума в резолюцию, проверка пересечения гексагонов с экраном
- `MockPoller` (profile=mock) — генерация тестовых событий для разработки UI

### 2\. Дашборд (`/api/v1/dashboard`)

- `DashboardService` — чтение трёх витрин (`marts/trends`, `marts/top_articles`, `marts/top_geo`), свёртка часовых точек в суточные для периода 30d
- Кэширование ответа на 60 секунд (`@Cacheable` с Caffeine) — свёртка считается раз в минуту, а не на каждый запрос
- Перевод периодов (`24h`/`7d`/`30d`) в формат витрин (`24h`/`168h`/`720h`) на бэке

### 3\. Обработка ошибок

- `GlobalExceptionHandler` — Problem Details для 400/503/500
- `BadRequestException` — семантическая валидация (bbox, zoom, period, limit)
- `YtReadException` — отдельный тип для ошибок YT (503 Service Unavailable)
- Catch-all `Exception.class` — защита от утечки внутренностей (токены, пути таблиц)

### 4\. Поллер очереди (`YtQueuePoller`)

- Чтение из `q_enriched` каждые 500 мс, курсор двигается **после** успешного put в кэш (гарантия at-least-once)
- Двухуровневый catch: `YtReadException` (warn, ретрай) vs `RuntimeException` (error со стеком)
- Счётчик `ytFailStreak` для эскалации warn → error при серии неудач

## Архитектурные решения

### Серверный расчёт H3-гексагонов вместо SDK Яндекс Карт

**Выбор:** используем Uber H3 на сервере (`H3GeoService`) вместо готовой геометрии от SDK Яндекс Карт на фронте.

**Почему это правильно:**

1. **Единый источник правды**

   - Все расчёты живут на бэке: кэш хранит события с ключом `h3_r9`, витрины агрегируют по H3, сервис фолдит в нужную резолюцию
   - Фронт получает готовые индексы, не дублирует логику
   - Изменение алгоритмов (другая резолюция, другой маппинг зума) — правка на бэке, фронт не меняется

2. **Производительность и кэширование**

   - Сервер считает фолдинг один раз для всех клиентов в пределах TTL кэша
   - SDK на фронте пересчитывал бы геометрию для каждого клиента отдельно
   - Stateless архитектура: бэк не хранит геометрию, он её вычисляет по запросу

3. **Независимость от фронтенд SDK**

   - Не привязаны к конкретной map-библиотеке (можем сменить Яндекс Карты на MapLibre/Leaflet без переписывания бэка)
   - Контракт REST API стабилен: `h3_index` — строка, фронт рисует её как хочет
   - Тестируемость: curl → JSON, без визуальной отрисовки и зависимостей от браузера

4. **Масштабируемость**

   - При 100 клиентах бэк делает один фолдинг (или несколько с разным кэшированием по zoom)
   - SDK на фронте делал бы 100 независимых расчётов
   - Серверный H3 — чистая арифметика (миллисекунды), не зависит от числа клиентов

5. **Гибкость резолюций**

   - Zoom → resolution маппинг живёт в yaml (`zoom-r3-max: 5`, `zoom-r6-max: 11`)
   - Можно менять пороги без перекомпиляции
   - Для 30d на дашборде используем r4 (крупные клетки), для карты — r3/r6/r9 в зависимости от зума

**Вывод:** серверный H3 — это контроль, производительность и независимость. Фронт получает готовые индексы и рисует их как хочет, бэк владеет всей логикой агрегаций.

### Тонкие контроллеры, толстые сервисы

- Вся бизнес-логика и валидация — в сервисах
- Контроллеры — только биндинг параметров и делегирование
- Валидация zoom/bbox переехала из контроллера в сервис (единое место правды)

### Безопасная проверка пересечения гексагонов с экраном

- Вместо «центр в прямоугольнике» (дыры на низком зуме) — три условия:
  - центр гексагона внутри экрана
  - любая вершина гексагона внутри экрана
  - любой угол экрана внутри гексагона
- Результат: нет дыр по краям карты при большом размере клеток

### Сортировка перед обрезкой

- `events.stream().sorted(...).limit(eventsCap)` — гарантируем, что `.limit(50)` берёт 50 самых свежих правок, а не первые 50 из конкатенации отсортированных кусков

### Конфигурация через yaml, ноль хардкода

- Все плавающие значения (zoom-min/max, пороги резолюций, window-minutes, TTL кэша) — в `application.yaml`
- Продуктовые решения правятся одной строкой конфига без перекомпиляции

### Проброс `event_ts` в DTO

- Фронт получает timestamp правки для «2 мин назад» и корректный выбор свежего `diff_url`

## (оптимизации и фичи)

### 1\. Предзагрузка с запасом (фронтенд)

- Фронт запрашивает данные для прямоугольника ×2–3 экрана
- При движении карты — локальная перерисовка из памяти (real-time, без запросов)
- Бэк не меняется: он уже принимает любой bbox

## Итог

Реализован полный MVP: живая карта с H3-гексагонами, дашборд с тремя витринами, кэширование, обработка ошибок, чтение из реальной очереди YTsaurus.

**Ключевые архитектурные решения:**

- Серверный H3 вместо SDK (контроль, производительность, независимость)
- Stateless REST API с кэшированием (масштабируемость)
- Единый источник правды на бэке (кэш \+ витрины)
- Problem Details для всех ошибок (стабильный контракт)
