# Документация

Разделы пронумерованы по порядку чтения: от «что делаем» через «как устроено»
к «как это эксплуатировать». Номер — часть имени папки, чтобы листинг сам собой
шёл в правильном порядке.

Если не знаешь, куда положить документ: описание границы между компонентами —
в `03-contracts`, причина принятого решения — в `04-decisions`, пошаговая
инструкция — в `05-runbooks`.

## 04-decisions — почему сделали именно так

Журнал архитектурных решений (ADR): одно решение — один файл, после мержа
не редактируется. Нужен, чтобы через месяц не обсуждать заново отвергнутые
варианты и чтобы было что ответить на защите.

- [README.md](04-decisions/README.md) — когда заводить ADR и список принятых.
- [template.md](04-decisions/template.md) — шаблон: контекст, варианты,
  решение, последствия.

## Правила ведения

**Когда обновляем**

- В том же PR, что и код. Документ соврал после мержа — PR не готов.
- Контракт правится **до** кода, а не после: сначала договорились, потом пишем.
- Документ устарел и никто его не чинит — удаляем. Врущий документ хуже, чем
  его отсутствие: на отсутствующий никто не сошлётся.

**Кто отвечает**

- У каждого документа один владелец (см. [roles.md](06-team/roles.md)).
  Править может любой, аппрувит владелец.
- Контракты — аппрув обеих сторон границы.
- Дежурный по интеграции на своей неделе проверяет, что документы не разошлись
  с тем, что реально в `main`.

**Как пишем**

- Markdown, строки до 90 символов — чтобы диффы читались по словам, а не целыми
  абзацами.
- Имена файлов — латиница, kebab-case.
- Текст по-русски; имена полей, таблиц, эндпоинтов — латиницей, как в источнике.
- Черновик помечаем строкой `> Черновик, не опорный документ` в начале файла.

**Чего не делаем**

- Не пересказываем код словами — он меняется быстрее, чем мы правим документы.
  Документируем решения, границы и причины.
- Не дублируем: одно правило живёт в одном месте, остальные на него ссылаются.
- Не оставляем «допишу потом» — либо пишем, либо заводим задачу.
