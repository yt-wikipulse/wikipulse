# Безопасность

Где проходят границы доверия, какие секреты держит система и как их менять,
какие ограничения есть сейчас и что обязан настроить тот, кто форкает
проект.

Куда сообщать об уязвимости — в [SECURITY.md](../../SECURITY.md) в корне.
Заголовки и CSP на реверс-прокси — в
[deploy/README.md](../../deploy/README.md).

## Границы доверия

Границ четыре, недоверенный вход среди них один.

**1. Браузер → бэкенд.** Единственный недоверенный вход. API публичный,
только чтение, все эндпоинты — `GET`. Всё, что приходит в query-параметрах,
проверяется на входе:

| Где | Что проверяется |
|---|---|
| `DashboardController` | `period` — ровно `24h`, `7d` или `30d`; `limit` — от 1 до 100 |
| `LiveMapService.validateInput` | `min_lng`/`min_lat` строго меньше `max_*`; `zoom` в границах `app.live.zoom-min`…`zoom-max` |
| `YtAggregatesRepository` | `period` ещё раз, по маске `^\d+h$`; `limit` зажимается в 1…1000 |

Повторная проверка в репозитории — не дублирование, а вторая граница: там
пользовательская строка попадает в текст запроса к YT.

**2. Бэкенд → YTsaurus.** Доверенное соединение по RPC с токеном. Запросы
собираются конкатенацией строк, поэтому в текст запроса не попадает ни одно
непроверенное значение: `period` прошёл через маску, `limit` — число,
а координаты и зум в запрос к YT не идут вовсе — живая карта считается
по кэшу в памяти процесса.

**3. Пайплайн → Wikimedia.** Только чтение публичных данных. В `User-Agent`
уходит контакт из `WIKIPULSE_CONTACT` — этого требует User-Agent policy
Wikimedia, без контакта поток могут закрыть.

**4. Бэкенд → браузер в ответе об ошибке.** Наружу уходит статичный текст:
`storage is temporarily unavailable` для `YtReadException` и `internal error`
для всего неожиданного. Пути таблиц, текст ошибки YT и стектрейсы остаются
в логе.

Бэкенд не публикует свой порт наружу: в `deploy/compose.yml` порты открывает
только контейнер `web`, а он проксирует `/api/*` внутрь сети compose.

## Секреты

| Секрет | Где живёт | Кто его видит | Ротация |
|---|---|---|---|
| `YT_TOKEN` | `deploy/.env` на сервере, окружение контейнеров; в операциях на кластере — `YT_SECURE_VAULT_YT_TOKEN` | процессы бэкенда и пайплайна | новый токен в веб-интерфейсе кластера, замена в `.env`, `docker compose up -d`, отзыв старого |
| `YMAPS_API_KEY` | `deploy/.env`, окружение бэкенда | **и браузер тоже** — уезжает в ответе `GET /api/v1/config` | новый ключ в кабинете, замена в `.env`, `docker compose up -d backend`; пересборка фронта не нужна |
| `DEPLOY_SSH_KEY` | GitHub Actions secrets | job выкладки | новая пара, публичная часть в `authorized_keys`, замена секрета, удаление старого ключа |
| `DEPLOY_HOST_FINGERPRINT` | GitHub Actions secrets | job выкладки | снять `ssh-keyscan` с доверенной машины, сверить с консолью сервера, заменить секрет |
| `key.pem` файлового сертификата | каталог на сервере, монтируется в Caddy только на чтение | Caddy | перевыпуск сертификата, замена файлов, `docker compose up -d web` |

Правила обращения с ними:

- **Токен, попавший в коммит, лог или скриншот, отзывается в кластере.**
  Удаление из файла ничего не чинит: копия уже разошлась.
- **Токен не передаётся аргументом командной строки.** Аргументы видны
  в списке процессов, в спеке YT-операции и в Spark UI. Джобы на кластере
  читают `YT_SECURE_VAULT_YT_TOKEN`, который YTsaurus кладёт в окружение
  операции сам.
- **Ключ Яндекс Карт — не секрет, а идентификатор с ограничением.** Он по
  устройству продукта попадает в браузер; защищает его только ограничение
  по HTTP Referer в кабинете разработчика.
- **В репозитории секретов нет.** `.gitignore` закрывает `.env`, `*.key`,
  `*.pem` и локальную конфигурацию стенда (`deploy/.env`,
  `deploy/compose.override.yml`, `deploy/tls-file.caddy`). Выкладка
  исключает эти же файлы из `rsync --delete`, поэтому они остаются
  на сервере и через CI не проходят.
- **Фикстуры ключей не содержат:** в `backend/src/main/resources/fixtures/`
  лежат данные, снятые через публичный API, а `mock` отдаёт пустой
  `ymaps_api_key`.

## Что сделано в коде

- Все контейнеры: `cap_drop: ALL` и `no-new-privileges`. Бэкенд и bigdata
  работают от непривилегированного uid 10001. `web` остаётся от root, но
  с единственной добавленной capability `NET_BIND_SERVICE` — иначе Caddy
  не займёт порты 80 и 443.
- Caddy отдаёт HSTS, `nosniff`, `Referrer-Policy`,
  `Cross-Origin-Opener-Policy` и CSP; `frame-ancestors 'none'`
  и `object-src 'none'` закрывают встраивание в чужой iframe и плагины.
- Отпечаток SSH-хоста для выкладки берётся из секрета
  `DEPLOY_HOST_FINGERPRINT`, а не из `ssh-keyscan` в workflow.
- Пока переменная `DEPLOY_HOST` не задана, workflow выкладки не
  запускается — форк не пытается молча выложиться на чужую машину.

## Текущие ограничения

- **Аутентификации и авторизации в API нет.** Данные публичные, записи нет,
  все эндпоинты — `GET`.
- **Ограничения частоты запросов нет.** Фронт опрашивает карту раз в 2,5
  секунды, и любой другой клиент может делать это чаще.
- **CORS не настроен.** Фронт и API живут за одним origin через Caddy;
  отдельный домен для фронта потребует явной настройки.
- **Секрет-менеджера нет**: секреты лежат в `.env` на машине и в секретах
  GitHub Actions.
- **Образы собираются на боевой машине**, а не в реестре: одна и та же
  машина оказывается билд-агентом и продом.
- **Ни подписи образов, ни SBOM, ни сканирования зависимостей в CI.**
  CI гоняет тесты и сборку.
- **Централизованного сбора логов нет** — только `docker compose logs`.
- **Инлайновый скрипт переключения фавиконки в `frontend/index.html`
  нарушает CSP.** В `script-src` нет `'unsafe-inline'`, поэтому браузер
  этот скрипт блокирует; чинится переносом скрипта в модуль, а не
  ослаблением политики.
- **Наблюдаемости почти нет**: метрик и трассировки не собирается, свежесть
  данных видна только по атрибутам витрин (`@computed_at`).

## Что обязан настроить форкер

1. **Свой кластер и свой `YT_TOKEN`.** Чужой токен в примере не лежит
   и лежать не может.
2. **Свой ключ Яндекс Карт с ограничением по Referer на свой домен.**
   Голый IP кабинет не принимает, нужен домен; формат поля — только хост.
3. **Секреты выкладки или её отключение.** Либо `DEPLOY_HOST`,
   `DEPLOY_USER`, `DEPLOY_DIR` и оба секрета в Settings → Secrets and
   variables → Actions, либо `.github/workflows/deploy.yml` удаляется.
4. **Права на файлы стенда:** `deploy/.env` и `key.pem` — только для
   владельца; каталог с сертификатами монтируется в Caddy на чтение.
5. **Проверить, что в форк не уехали чужие секреты.** Файлы `.env` не
   отслеживаются git, но остаются в рабочем дереве.
