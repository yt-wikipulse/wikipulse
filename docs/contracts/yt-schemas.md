# Контракт: схемы таблиц и очередей YT

Граница между пайплайном и бэкендом: пайплайн пишет данные, бэкенд их читает.

Контракт описывает **обязательный минимум**, которого хватает живой карте и
дашборду. Лишние колонки в реальных таблицах не мешают. Имена полей —
`snake_case`.

## Где лежат пути

Корень всех путей — переменная `YT_BASE_PATH`, по умолчанию `//home/wikipulse`.
Литералов путей в коде нет: пайплайн собирает константы из `BASE` в
[`bigdata/src/bigdata/paths.py`](../../bigdata/src/bigdata/paths.py), бэкенд —
из ключа `yt.base-path` в `application.yaml` через `${yt.base-path}/…`.

## Объекты

| Путь | Тип | Пишет | Читает |
|---|---|---|---|
| `q_raw` | ordered dynamic (queue) | ингестор SSE | SPYT-джоба обогащения |
| `dict/coords` | sorted dynamic, `unique_keys` | загрузчик справочника | SPYT-джоба обогащения |
| `q_enriched` | ordered dynamic (queue) | SPYT-джоба обогащения | бэкенд, архиватор |
| `history/t_history` | static | архиватор | SPYT-джоба витрин |
| `marts/trends` | dynamic | SPYT-джоба витрин | бэкенд |
| `marts/top_articles` | dynamic | SPYT-джоба витрин | бэкенд |
| `marts/top_geo` | dynamic | SPYT-джоба витрин | бэкенд |

Служебные узлы вне контракта, их заводит `init-tables`: `consumers/c_enrich`
(vital-консьюмер `q_raw`), `consumers/c_archive` (vital-консьюмер
`q_enriched` — им архиватор и держит трим), `consumers/c_backend`
(non-vital консьюмер `q_enriched`: живая карта отстаёт, но очереди тримиться
не мешает), `checkpoints/c_enrich` (чекпойнт Spark Structured Streaming),
`lib` и `src` (артефакты SPYT, заливаются командой `upload-artifacts`).

## q_raw

Сырые правки из потока Википедии. Схема объявлена целиком в
`scripts/init_tables.py`, `strict` не отключается.

| Поле | Тип | Описание |
|---|---|---|
| `$timestamp` | uint64 | служебное поле очереди |
| `event_id` | string | имя вики и номер новой ревизии через вертикальную черту |
| `wiki` | string | `enwiki`, `ruwiki` — ключ джойна |
| `title` | string | заголовок статьи, подчёркивания заменены пробелами — ключ джойна |
| `url` | string | ссылка на статью (`title_url` из потока) |
| `event_ts` | uint64 | время правки, unix-секунды |
| `length_update` | int64 | прирост длины статьи в байтах, бывает отрицательным |
| `diff_url` | string | ссылка на диф правки (`notify_url` из потока) |

Фильтр на входе (`ingestor.event_to_row`) пропускает дальше только события,
у которых одновременно: `bot = false`, имя вики оканчивается на `wiki`, не
сводится к одному этому суффиксу и не входит в список неязыковых проектов
(`wikidatawiki`, `commonswiki`, `metawiki`, `abstractwiki`), `namespace = 0`,
`type` — `edit` или `new`, и есть `revision.new`. Разбор полей источника —
в [data-sources.md](data-sources.md).

## dict/coords

Справочник координат из дампа Wikidata. Динамическая смонтированная таблица,
отсортированная по ключу джойна `(wiki, title)`, со схемой `unique_keys = true`:
обогащение читает её через `lookup_rows`, который работает только с такой.

| Поле | Тип | Ключ | Описание |
|---|---|---|---|
| `wiki` | string | да | языковой раздел |
| `title` | string | да | заголовок статьи |
| `lat` | double | | широта |
| `lon` | double | | долгота |

В справочник попадают только сущности со свойством `P625` (координаты),
и только их сайтлинки в языковые разделы Википедии. Пары `(wiki, title)`
загрузчик дедуплицирует перед записью: схема с `unique_keys` иначе не
примет данные.

## q_enriched

Главный объект контракта: из него бэкенд строит карту.

| Поле | Тип | Описание |
|---|---|---|
| `event_id` | string | идентификатор правки, он же `id` в ответе API |
| `title` | string | заголовок статьи |
| `url` | string | готовая ссылка, бэкенд её не собирает |
| `h3_r9` | string | ячейка H3 уровня 9 |
| `event_ts` | uint64 | время правки, unix-секунды |
| `length_update` | int64 | прирост длины статьи в байтах |
| `diff_url` | string | ссылка на диф правки |

**Только уровень 9.** Ячейки крупнее и бэкенд, и джоба витрин получают из
неё арифметикой H3 (`cellToParent`). Класть в очередь заранее свёрнутые
ячейки не нужно.

**Правки без координат в очередь не попадают.** Джоба обогащения ищет пару
`(wiki, title)` в справочнике и статью без геометки в очередь не кладёт.

Бэкенд читает очередь консьюмером `c_backend`: `pull_consumer` за страницей,
`advance_consumer` после укладки в кэш. Позиция переживает рестарт, потому
что живёт в самой очереди, а не в памяти поллера. Дедупликация по `event_id`
и окно в 30 минут — в кэше бэкенда, см.
[backend.md](../architecture/backend.md).

## history/t_history

Статическая таблица-архив: источник всех витрин дашборда. Архиватор
дописывает новые строки `q_enriched` страницами по 5000, а позицию хранит
в консьюмере `c_archive`. Схема повторяет `q_enriched`.

| Поле | Тип | Описание |
|---|---|---|
| `event_id` | string | идентификатор правки, ключ дедупа в витринах |
| `title` | string | заголовок статьи |
| `url` | string | готовая ссылка |
| `h3_r9` | string | ячейка H3 уровня 9 |
| `event_ts` | uint64 | время правки, unix-секунды |
| `length_update` | int64 | прирост длины статьи в байтах |
| `diff_url` | string | ссылка на диф правки |

Дубли `event_id` возможны — архиватор может упасть между записью страницы
и сдвигом консьюмера; джоба витрин дедуплицирует по `event_id` сама.

## marts/trends

Количество правок по часам. Накопительная витрина: каждый пересчёт
перезаписывает бакеты попавшего в окно диапазона часов, старые часы
остаются как история.

| Поле | Тип | Ключ | Описание |
|---|---|---|---|
| `bucket_ts` | uint64 | да | unix-время начала часа |
| `edits_count` | int64 | | число правок за час |

**Колонки `period` здесь нет.** Все три окна шедулера (24, 168 и 720 часов)
пишут в одни и те же часовые бакеты, различаясь только глубиной пересчёта.
Бэкенд поэтому выбирает точки не по периоду, а условием
`bucket_ts >= now - длительность периода`.

## marts/top_articles

Топ правимых статей за окно.

| Поле | Тип | Ключ | Описание |
|---|---|---|---|
| `period` | string | да | окно пересчёта в часах: `24h`, `168h`, `720h` |
| `rank` | int64 | да | место в топе, с 1 |
| `title` | string | | заголовок статьи |
| `url` | string | | ссылка на статью |
| `edits_count` | int64 | | правки статьи за окно |

При равных `edits_count` выше ставится статья выше по алфавиту — порядок
стабилен между пересчётами.

## marts/top_geo

Топ гео-мест за окно. Ячейки `h3_r9` сворачиваются до **резолюции 6** —
это параметр `--h3-res` джобы `spyt_marts` и его значение по умолчанию;
шедулер параметр не переопределяет.

| Поле | Тип | Ключ | Описание |
|---|---|---|---|
| `period` | string | да | окно пересчёта в часах: `24h`, `168h`, `720h` |
| `rank` | int64 | да | место в топе, с 1 |
| `h3_parent` | string | | ячейка H3 резолюции 6 |
| `top_title` | string | | самая правимая статья ячейки |
| `top_url` | string | | её ссылка |
| `edits_count` | int64 | | правки всех статей ячейки за окно |
| `articles_count` | int64 | | уникальных статей ячейки за окно |

Резолюция 6 — единственное место, где витрины расходятся с живой картой:
карта отдаёт ячейки резолюций 3, 4, 5, 6, 8 и 9 в зависимости от зума,
и совпадение с ячейкой витрины случается только на одной ступени лестницы.
Переход «клик по строке дашборда → карта» поэтому ведёт в центр ячейки,
а не подсвечивает её один в один.

Джоба витрин проставляет на каждую таблицу отладочные атрибуты `@computed_at`
и `@window_hours`, на топы — `@top_n`, на `top_geo` — `@h3_res`. Бэкенд их
не читает.

## Известные ограничения

**Топы не чистятся от хвоста.** `top_articles` и `top_geo` пишутся
`insert_rows(update=True)` по ключу `(period, rank)`. Если следующий
пересчёт вернёт меньше строк, чем предыдущий, старые места с большими
`rank` останутся в таблице.

**Трим идёт за архиватором, а не за бэкендом.** `c_archive` vital,
`c_backend` — нет, поэтому очередь срезается по позиции архиватора. Если
бэкенд отстанет от неё больше чем на окно трима, часть событий он не увидит
вовсе: для живой карты это приемлемо, для архива — нет.
