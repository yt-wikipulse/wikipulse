# Как мы работаем в репозитории

Цикл задачи — в [taskflow.md](taskflow.md). Здесь только git.

Язык репозитория — русский: коммиты, документация, комментарии в коде.
Имена полей, таблиц и эндпоинтов — латиницей, как в источнике.

## Ветки

Trunk-based: `main` — единственная долгая ветка, всё остальное живёт 1–2 дня.

- `main` защищена, прямых пушей нет.
- Имя ветки: `<тип>/<номер задачи>-<суть>` — `feat/14-sse-producer`.
- Типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`.
- После мержа ветку удаляем.

Не заводим: долгие ветки на трек (`pipeline`, `backend`), `develop`, форки.

## Мерж

- Squash: от задачи в `main` остаётся один коммит.
- Перед вызовом ревьюера подтянуть `main`: `git pull --rebase origin main`.
- Мержим в течение недели, не копим к субботе.

## Контракты

Изменение [контракта](../docs/03-contracts/) едет **отдельным PR и мержится
первым**, до реализации. Иначе конфликт придёт в самый важный файл проекта.

## Коммиты

Внутри ветки — как угодно, при squash они схлопнутся.
В `main` попадает один коммит на задачу, его тема — заголовок PR:

```
<тип>: суть
```

Если из темы неясно «почему» — пиши тело.

## PR

Автор проверяет перед вызовом ревьюера:

- [ ] ветка обновлена от `main`;
- [ ] в описании сказано, как проверить;
- [ ] контракты обновлены, если PR их менял;
- [ ] нет секретов, `.env`, локальных путей, отладочных выводов.

Ревьюер — из соседнего трека по кольцу из [roles.md](roles.md).
Если назначить его в интерфейсе не получается — просто пишем ему в чат
со ссылкой на PR. Мержит автор после аппрува.

## Защита

В начале фиче-фриза ставим тег на рабочем коммите:

```bash
git tag v1.0-defense && git push origin v1.0-defense
```

## Не решено

Срок ревью PR и число аппрувов — вопросы на встречу команды.
